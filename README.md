# 포코피아 도감 프로젝트 — 작업 인계 문서

이 문서는 다른 작업창(새 대화)에서 이어서 작업할 수 있도록 현재 상태와 작업 이력을 정리한 것입니다.

## 프로젝트 개요

- 메인 파일: `index.html` (= 배포/작업용 최종본)
- 동일 사본: `포코피아_도감.html` (사용자 요청으로 만든 로컬 백업, index.html과 항상 내용 동일하게 유지)
- ⚠️ 이 프로젝트는 같은 폴더에 있는 "포켓몬 퀴즈(오늘의 포켓몬은 뭘까요)" 프로젝트(`github-upload/`, `pokemon-shadow-quiz-v*.html`)와 **완전히 다른 별개 프로젝트**입니다. 혼동하지 마세요.
- GitHub 저장소 정보는 아직 모릅니다. 배포 관련 작업 시 사용자에게 레포 주소부터 확인 필요.

## 데이터 구조 (index.html 내 단일 `<script>`)

JSON.parse 가능한 형태로 아래 5개 블록이 있습니다 (순서대로 파일 내 등장):

- `const DATA=[...]` — 포켓몬 313마리(뮤 이후 E001~E005 5마리 포함, 총 313개 항목). 각 항목: `{no, dex, name, types, flavor, specs, img}`
- `RECIPES=[...]` — 레시피 24개. `{icon, name, flavor, ings, req?, fb?}` (fb = onerror 대체 아이콘, 현재는 사용 안 함/제거됨)
- `ING_ICON={...}` — 재료 아이콘 19개 (키: 재료명 → 값: img 경로)
- `SPEC_ICON={...}` — 특기 아이콘 31개
- `FLAVOR_ICON={...}` — 맛 아이콘 6개
- `TYPE_COLORS`/`TYPE_EN` — 타입 18종 (색상/영문 매핑, 이미지는 `img/type_*.png` 템플릿으로 참조)

카드 렌더링(도감번호 표시): `<span class="no">${...}</span>` — no가 "E"로 시작하면 그대로 표시, 숫자면 3자리 패딩(`padStart(3,'0')`). `#` 기호는 제거됨(원래 있었으나 삭제).

## img 폴더 파일명 규칙 (전부 로마자, 영어 발음표기)

GitHub는 한글 파일명 이슈가 있어서(사용자 요청) 전부 로마자로 통일했습니다.

- DEX 스프라이트: `img/{번호}_{로마자이름}.png` (번호는 3자리 패딩 또는 E001~E005 그대로, 예: `001_isanghaessi.png`, `197_seuteurindeo_haihan_moseup.png`, `E005_jirachi.png`)
- 레시피 아이콘: `img/recipe_{로마자이름}.png`
- 재료: `img/ing_{로마자이름}.png`
- 특기: `img/spec_{로마자이름}.png`
- 맛: `img/flavor_{로마자이름}.png`
- 타입 아이콘(`img/type_*.png` 18개)과 `img/monsterball.png`(구 ball.png)는 원래도 알아보기 쉬운 이름이라 건드리지 않음

로마자 변환은 자체 구현한 Revised Romanization 알고리즘 사용(외부 라이브러리 설치 불가 — 샌드박스 pip가 네트워크 차단됨). 초성/중성/종성 매핑 + 연음(linking) 규칙 포함. 같은 폴더의 `romanize_tool.py`에 전체 코드 있음 — 앞으로 이름을 더 추가/변경할 때 재사용 가능.

**현재 img 폴더 총 파일 수: 412개** (DEX 313 + 레시피 23 + 재료 19 + 특기 31 + 맛 6 + 타입 18 + monsterball 1 + E001~E005는 DEX 313에 포함, 세부 합계는 근사치이며 정확한 수는 `index.html`의 이미지 참조 개수와 항상 대조해서 확인할 것).

## ⚠️ 알려진 이슈: 대량 파일 작업 시 일시적 폴더 분산 현상

작업 중 img 폴더 안에 `img1`, `img2`, `img3`, `img\img` 같은 하위 폴더가 생기면서 파일들이 거기로 흩어져 보인 적이 있었습니다(700개 이상의 파일을 빠르게 rename/delete 했을 때 발생). **원인은 확실하지 않으나, 몇 분 뒤 재확인하니 자동으로 원래대로(img 바로 밑) 합쳐져 있었습니다** — OneDrive 등 클라우드 동기화나 백그라운드 프로세스가 대량 파일 이벤트를 처리하는 동안 생기는 일시적 현상으로 추정됩니다.

**다음에 이런 상황을 다시 만나면:**
- 당황해서 바로 손대지 말고, 1~2분 기다린 후 다시 확인할 것
- 확인은 bash보다 `Glob`/`Read` 도구가 더 신뢰할 수 있음(다만 이번엔 Glob도 과도기에는 일시적으로 불일치하는 결과를 보여준 적 있었음 — 완전히 안정된 상태인지는 같은 조회를 2~3번 반복해서 일치하는지로 판단)
- 최종 확인은 `index.html`의 이미지 참조 경로들이 전부 실제 파일로 존재하는지 매칭하는 스크립트로 할 것 (`romanize_tool.py` 옆에 검증용 로직 참고 가능)
- 대량 파일 작업(수백 개 단위 rename/delete)은 가능하면 한 번에 몰아서 하지 말고 배치로 나눠서 하고, 각 배치 후 안정화를 기다리는 편이 안전할 수 있음
